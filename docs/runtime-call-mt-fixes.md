# Диагностика завершения GSM-вызовов и повтора MT SMS

## Завершение вызова по `+CLCC`

Переданные строки `+CLCC: 1,1,6,0,0,"+79958528857` и `+CLCC: 1,0,6,0,0,"+79958528857` содержат оборванный quoted-number и modem state `6`. В `src/at_parse.c:at_parse_dsci()` документация формата `^DSCI` приводит state `6` как значение события; enum `CALL_STATE_RELEASED` в `src/cpvt.h` также имеет значение 6. При этом обычный строгий CLCC parser допустимо отвергал status выше 5: `src/clcc_parser.c:clcc_parse_line()` не принимал vendor release, а `src/at_response.c:at_response_clcc()` помечал весь snapshot invalid и не вызывал `handle_clcc()` для строки. В результате release не попадал в `defer_call_release()` / `cpvt_change_state(CALL_STATE_RELEASED)`, канал оставался активным; поздний локальный hangup мог отправить `AT+CHUP/QHUP` вместо реакции на уже завершённый GSM вызов.

Исправление ограничено отдельным `clcc_parse_release_prefix()`: он принимает только полный identity-префикс с ненулевым индексом, направлением 0/1, точным state 6, voice mode 0 и допустимым multiparty. Номер и его кавычки для release не нужны. Такой release передаётся в существующий `handle_clcc()` и ставит тот же durable-ID barrier, что DSCI. **Сам повреждённый snapshot остаётся invalid** и не может сам подтвердить отсутствие звонка: AT-обработчик ставит последующий CLCC, и только валидный свежий snapshot без соответствующего индекса завершает вызов и очередь hangup на Asterisk channel. Если slot присутствует, candidate остаётся открытым. Другие состояния, типы вызова и malformed identity по-прежнему отклоняются.

Тест `clcc-parser` проверяет строгие частичные incoming/outgoing release-префиксы, отказ соседних malformed полей, invalid snapshot, retry, затем fresh-empty finish, exactly-once missed notification и отсутствие missed классификации исходящего звонка. Тест вызывает production parser/snapshot/SQLite helpers, но не запускает static Asterisk `at_response_clcc()`/taskprocessor или реальный modem event stream; этот runtime boundary остаётся непроверенным.

## MT SIM→Flexisip retry

`mt_queue` (SIM→приложение) остаётся отдельной от `mt_out` (приложение→SIM). Производственный путь: `mt_retry_threadproc()` → `smsdb_mt_pick_retry()` → `mt_send_row()` → PJSIP MESSAGE → `mt_msg_response_callback()` → `smsdb_mt_set_result()`. PJSIP timeout callback преобразуется в status 408; 3xx/4xx/5xx и transport failure оставляют ту же MID в `retrying`, увеличивают attempts и задают `next_retry_at`; следующий проход выбирает её только когда срок наступил и attempts не исчерпан. 2xx переводит эту MID в `delivered`; повторный picker её уже не выбирает. 202 и provisional response остаются `queued` у Flexisip и retry semantics не меняют.

Retry-политика теперь выделена в production `src/mt_retry.[ch]`; её ответ-функция используется callback и локальной ошибкой подготовки/отправки. `MT_RETRY_PICK_SQL` является общим запросом для `smsdb_mt_pick_retry()` и настоящего SQLite test harness: `new` можно отправить сразу, `retrying` — только при `next_retry_at <= now AND attempts < max_attempts`, FIFO по `created_at`. Поэтому после временного timeout строка не потеряна: при старте/перезапуске retry thread она остаётся в SQLite и выбирается после due времени. Конечный лимит попыток сохранён; строка, достигшая лимита, намеренно больше не выбирается.

`test/mt-retry` строит тот же production SQL на SQLite-файле, проверяет до/на due boundary, закрытие и повторное открытие DB между 408 и следующей попыткой, затем эмулирует доступного получателя успешным 200 и проверяет `delivered` и отсутствие дальнейшей выборки. Также проверяются 1xx/202, конечный лимит и некорректные параметры. Тест покрывает общий policy/helper и production query, но не живой PJSIP TLS socket/callback dispatch.

### Установленная причина malformed `From` и исправление

Проверены две стороны в одном временном окне; сравнивались внешние `docker logs --timestamps` в UTC, поэтому часовой пояс контейнеров не создаёт сдвига: Asterisk `orangepi-asterisk-asterisk` pane `w3:p6Y`, Flexisip pane `w3:p5H` (внешние timestamps обеих сторон UTC). В Asterisk `2026-10-23T15:24:32.093707569Z` отправляет MID `sim1-1792699407-1`, attempt 25/300, с `from MegaFon@`; в Flexisip `15:24:32.286Z` (внутренняя метка `15:24:32:285`) виден совпадающий MESSAGE с canonical/parsed `From` `sip:sip%3AMegaFon@@sipsis.keblog.ru` и ответ `400 Bad Request`. Та же связанная пара повторяется для MID `sim1-1792699419-2`: Asterisk `15:24:53.249539054Z`, Flexisip `15:24:53.443Z`. Почти одновременно Asterisk PJSIP сообщает, что отбросил 443-byte TLS packet из `43.249.33.17:443` из-за syntax error parsing From (line 3, column 26); callback позднее сохраняет 408 и retry примерно через 3607 секунд. Все отметки сверены по UTC timestamps, не по локальным часам контейнеров.

Сырые packet bytes/raw header не сохранены, но коррелированные MIDs и время, фактический `from MegaFon@` в Asterisk send log, Flexisip parsed/canonical MESSAGE `From` и его 400, а также production builder `src/mt_task.c` доказывают происхождение именно этого malformed instance: прежний `snprintf("sip:%s@%s", cur.from_num, domain)` получал sender `MegaFon@` и строил два `@` разделителя. Это доказательство данного случая не следует обобщать на любой PJSIP parse error.

Asterisk cached API `ast_sip_update_from(pjsip_tx_data*, char*)` (заголовок `asterisk/res_pjsip.h`) принимает полную SIP URI либо `user[@domain]`; implementation `res/res_pjsip.c` парсит полную URI через `pjsip_parse_uri()` и копирует её user/host/port в исходный From header. Поэтому production `mt_from_uri_build()` сначала percent-encode-ит reserved bytes sender user-part и строит полную URI; `MegaFon@` становится `sip:MegaFon%40@sipsis.keblog.ru`, сохраняя sender identity, но не создавая лишний authority delimiter. Control bytes, CR/LF, пустые поля, malformed host/port и недостаточный буфер отклоняются до вызова API. Ошибка генерации/API не отправляет MESSAGE и записывает retryable local failure; From generation для IMDN использует тот же builder.

`test/mt-from` проверяет точное `MegaFon@` regression, numeric/alphanumeric sender, percent-encoding reserved delimiters, DNS+port и bracketed IPv6 host, а также пустой/malformed input, CR/LF/header injection и buffer errors. Это тестирует именно URI builder; PJSIP header mutation и итоговая сериализация wire header не выполняются в dependency-light harness. `test/mt-retry` отдельно проверяет production policy/SQLite picker цепочку 400 → due retry после restart → success 200 → delivered/no further pick, а также 408 и transport-error policy. Живого Asterisk/Flexisip roundtrip после изменения не запускали; raw packet bytes всё ещё отсутствуют.

## Неблокирующая история вызовов

До изменения `handle_clcc()` и `channel_call()` синхронно вызывали `smsdb_call_*()`, которые входили в `SCOPED_DB` и выполняли SQLite на AT/state path. Теперь `smsdb_call_start/answer/set_index/finish/release_confirm/active_id` используют `call_log_async.[ch]`: producer берёт только `pthread_mutex_trylock`, копирует event в fixed-size bounded ring, а единственный writer thread последовательно выполняет SQLite вызовы. Свободное место в queue не зависит от готовности DB; queue mutex не удерживается во время SQLite I/O. `call_log_async_active_id()` делает только RAM lookup. Стартовая выборка `MAX(call_log.id)+1`, schema/recovery и создание writer происходят при module initialization до звонковых событий, не в критическом call path.

Stable ID остаётся `call-<rowid>`: при старте модуля rowid allocator seed-ится выше и `MAX(call_log.id)`, и сохранённого `sqlite_sequence` AUTOINCREMENT high-water mark; это не позволяет после удаления последней строки и restart выдать прежний ID новому вызову. `call_log_async_seed_id()` — общий production/test seam для этого расчёта. Producer резервирует следующий ID под queue lock, а writer вставляет его явно через `call_log_start_reserved()`. Предварительно принятый FINISH оставляет incoming ID в RAM map, пока SQLite writer не подтвердит commit; при DB failure запись остаётся доступной для retry/history handling, а после успешного commit точное поколение удаляется из map. Это не делает очередь durable: непроизведённое/неуспевшее committed событие всё ещё теряется в заявленном RAM crash/overflow window. Incoming повтор с теми же device/index дедуплицируется active map; подтверждённый successor generation получает новый ID, а повторно используемый индекс после finish может создать следующий вызов. `START → ANSWER/index → FINISH` сохраняют FIFO порядок. Finish writer вызывает прежнюю транзакцию `call_log_finish()`, которая меняет missed status и вставляет одну `mt_queue` запись атомарно и идемпотентно. Startup recovery по-прежнему завершает только ранее committed незакрытые строки.

Очередь имеет 256 слотов и фиксированные event buffers, per-event malloc отсутствует. Lock contention, заполнение очереди, неверный/слишком длинный payload или недоступный writer возвращают ошибку немедленно; DB I/O никогда не выполняется как fallback. Поступивший event не теряется из-за per-event allocation, но ошибка enqueue сообщает, что history event не принят. Ошибка reserved START оставляет сам звонок/набор продолжаться; если release event не имеет stable ID, fresh valid CLCC всё равно завершает CPVT/channel по индексу, без записи отсутствующей истории. Для принятого release candidate ошибка async FINISH оставляет candidate для следующего snapshot, но не задерживает modem-confirmed channel hangup. Полная очередь может привести к пропуску записи/статуса истории или missed notice — это явно логируется и не блокирует звонок.

Shutdown сначала останавливает device producers, затем `smsdb_atexit()` сигнализирует writer-у, дожидается drain/join и только после этого закрывает SQLite. Принятое пользователем RAM FIFO допускает loss window: аварийный процесс до SQLite commit теряет события, которые ещё были только в памяти; committed rows переживают restart и проходят обычный recovery. Durable spool намеренно не добавлялся. Тест `call-log-async` проверяет FIFO order, start dedupe, answered/missed status, exactly-once queue, закрытие/reopen SQLite и reseed, SQLite lock при быстром enqueue, bounded queue rejection, отсутствие строки до writer commit (демонстрация RAM-only окна), DB schema failure и продолжение writer после ошибки. Полный Asterisk callback/device stream не запускался.

## Другие строки запуска

- `stasis minimum_size`, зависимые `res_stasis_broadcast`/`app_stasis_broadcast` и отсутствующая xmldoc documentation — startup/configuration/dependency warnings, к CLCC parsing и `mt_queue` callback/retry отношения не доказано.
- `AT+CPCMREG=0 rejected; retry once with legacy command` — modem initialization compatibility path; не связано с SIP MT retry или CLCC release.
- Строки CLCC state 6 сопоставляются с partial release parsing; call `call-3` answered по Asterisk bridge logs, но история до фиксации могла сохранить `answered=no`, потому что SMS/call path не обработал release state.
- MT `408` после parse error соответствует transient SIP transaction outcome и due exponential retry. На попытке 25 default max delay уже равен 3600 s (+ jitter 0..10); это существующий backoff, не новое изменение. Лог `AT+CPCMREG` «retry once» к SMS retry не относится.
