# Шаг 4: долговременный журнал вызовов и уведомления

## Область

Этот шаг добавляет только запись вызовов и уведомление о missed. Он не добавляет счётчики главной страницы, web-историю вызовов, AT-страницу и не меняет доставку/retry `mt_queue`.

## Схема и устойчивый ID

`call_log` содержит одну строку на звонок: `id` (SQLite `AUTOINCREMENT`), `device` (имя SIM/устройства, например `sim1`), `number`, UTC `started_at`, `direction`, временный `call_idx`, `answered`, `finished`, `ended_at`. Типы `incoming`, `outgoing`, `missed`; missed — это входящий без ответа, а не отдельное направление.

Идентификатор наружу формируется как `call-<id>`. Он является PK строки, переживает перезапуски и никогда не выводится из modem `call_idx`. Последний хранится только для нахождения активного вызова, когда PBX-канал не создавался. Повторный CLCC входящего события с тем же device/index находит открытую запись; после завершения новая жизнь того же индекса создаёт новый AUTOINCREMENT ID. Для PBX-вызова `cpvt.call_log_id` переживает состояния канала; Asterisk uniqueid не обязателен и не является источником истины. Источник идентичности — durable database row.

## Источники событий и безопасная корреляция release

`at_response_clcc()` разбирает строки `+CLCC` (индекс, направление, состояние, mode, multiparty, номер, type); освобождённая строка обычно не входит в snapshot. Любая строка `+CLCC`, которую нельзя разобрать, либо запись с некорректным индексом/направлением/состоянием/mode/multiparty помечает весь ответ как invalid: последующий terminal OK не подтверждает отсутствие, pending release остаётся открытым и response task ставит новую CLCC-проверку. Только следующий полный корректный ответ может принять решение. `at_response_dsci()` читает `^DSCI` (индекс, направление, state, type, number, number type), а `at_response_qind()`/`at_parse_qind_cc()` — `+QIND: "ccinfo"` с индексом, направлением, state, mode, multiparty, номером и type. DSCI/QIND release подаются в `handle_clcc()` напрямую; ни один из форматов не содержит поколения вызова, устойчивого call ID или времени старта. Modem `call_idx` поэтому не доказывает, что поздний release относится к текущей строке. AT reader подаёт ответы в per-device taskprocessor, где обработка берёт `pvt->lock`; unsolicited DSCI/CCINFO release может прийти между строками ответа CLCC и его завершающим OK.

Release event больше не завершает строку по `device+call_idx`. Вместо этого обработчик копирует устойчивый ID кандидата (из `cpvt` либо lookup открытого incoming для no-channel случая) и ставит отдельный `AT+CLCC`. До принятия решения считаются уже ожидающие CLCC-команды; их ответы пропускаются как старые. Snapshot отмечает любой занятый modem index до фильтрации типа/состояния. На завершающем OK свежего snapshot занятый index без известного successor отменяет кандидата; подтверждённое отсутствие завершает именно сохранённый ID. Если до snapshot приходит unsolicited DSCI/CCINFO `INCOMING` или `WAITING` для того же индекса, это сигнал нового поколения: production helper создаёт отдельный устойчивый ID и связывает его с release-кандидатом. Повторы DSCI/CCINFO используют этот successor, а CLCC poll продолжает дедуплицировать по текущей открытой строке. При busy snapshot известное старое поколение завершается как missed, successor остаётся открытым; ACTIVE фиксируется по его ID. AT error/timeout не считается отсутствием; кандидат сохраняется, после обработки завершённой команды response-task немедленно ставит следующую сериализованную CLCC-проверку. Ошибка постановки запроса также не завершает вызов; последующее событие повторно пытается поставить pending проверку.

Новый unsolicited incoming различается от повторного CLCC poll именно по источнику события и release barrier; тест production-used unified decision/start helper воспроизводит `RELEASED(A) → DSCI ACTIVE(B)` первым событием → busy snapshot → повторный `ACTIVE(B)`; результат — два ID, missed для A и одна queue row, answered incoming B. CLCC poll и повторный DSCI используют successor без третьей строки. Принципиальная граница остаётся для переиспользования индекса без наблюдаемого нового unsolicited start: modem CLCC/DSCI/CCINFO не содержат generation ID, поэтому при одном лишь занятом snapshot невозможно доказать принадлежность. В этом случае поведение остаётся консервативным и не помечает занятую строку missed.

## Начало, переходы и завершение

- `handle_clcc()` создаёт/находит входящую запись для `INCOMING` и incoming `WAITING` **до** проверки `pvt_enabled()` и запуска PBX. Поэтому отключённый голосовой канал, ошибка `channel_new()` и ошибка `ast_pbx_start()` не скрывают сам звонок.
- Исходящий журнал создаётся в `channel_call()` до ATD. Ошибка постановки ATD завершает запись как `outgoing`; она никогда не создаёт missed.
- Подтверждённый `ACTIVE` фиксирует `answered=1` для входящего и исходящего вызова. Incoming использует существующий stable-ID flow; outgoing получает ID из `cpvt.call_log_id`, связанного с `call-<rowid>`, и не ищет целевую строку по номеру или текущему/повторно используемому `call_idx`. SQL выполняет одно идемпотентное `UPDATE` только по первичному ключу открытой строки; повторный ACTIVE не меняет другие вызовы. Направление не меняется: answered outgoing остаётся outgoing, а unanswered outgoing остаётся `answered=0` без missed. Завершение unanswered incoming только тогда переводит его в missed и ставит уведомление.
- `RELEASED` от CLCC/DSCI сначала проходит snapshot correlation выше; только подтверждённое отсутствие завершает запись. Тайм-аут приложения использует точный `cpvt.call_log_id` в `channel_hangup()`. Повторный finish no-op. Абандон без PBX-канала проверяется тем же fresh snapshot; outgoing fail/no-answer остаётся outgoing.
- При старте БД открытые записи восстанавливаются отдельными finish-транзакциями: исходящие закрываются как outgoing, answered incoming остаются incoming, неотвеченные incoming атомарно переводятся в missed и получают очередь. Если процесс завершится посреди восстановления, следующий запуск продолжит с первой незавершённой строки; уже закрытые строки повторно не уведомляются.

## missed -> MT queue

Для missed формируется стабильный `mid=missed-<call row id>`, `from_num=missed-call`, текст `Пропущенный вызов: SIM <device>, номер <number>, время начала <UTC started_at>`. Число назначения звонящего не используется как адрес доставки; `mt_queue.device` задаёт нужную SIM и существующую привязку доставки.

`call_log_finish()` вызывается из lifecycle callbacks, где может быть уже захвачен device/pvt lock; затем он берёт общий SQLite connection mutex и `BEGIN IMMEDIATE` от чтения статуса до изменения строки, вставки и COMMIT. Порядок — device lock → SQLite mutex; внутри транзакции нет обратного захвата device lock и нет обращения к Asterisk callbacks. Этот инвариант сохраняет сериализацию SQLite и исключает lock inversion с call path. Вставка выполняется существующим production helper `sms_mt_queue_put()` из `sms_multipart.c`, с теми же `mt_queue` столбцами/default state, но находится в транзакции вместе со сменой `incoming→missed`. Ошибка вставки или COMMIT вызывает rollback; невозможно оставить missed без durable MT row. Стабильный MID и `finished=1` делают повторные CLCC/hangup/recovery идемпотентными. MT worker, retry и delivery state не меняются.

Схема создаётся `CREATE TABLE/INDEX IF NOT EXISTS` в отдельной транзакции после базовой SMS schema transaction. Ошибка новой call schema/recovery логируется, но не отменяет уже существующий SMS DB startup или звонки; call logging ошибки остаются отдельной ошибкой функции/логом, исходное AT/PBX поведение продолжается. `call_log` SQL helper не владеет соединением; DB mutex удерживается вокруг транзакций, prepared statements освобождаются внутри вызова. Вложенный `sms_mt_queue_put()` не начинает собственную транзакцию и работает под тем же lock/transaction.

## Проверки и границы

`ctq_call_log_test` вызывает production SQL/correlation helpers с временной in-memory SQLite: outgoing fail без уведомления; answered incoming; повторный incoming и WAITING event; missed с SIM/номером/UTC/start/type/text/sender; две SIM; повторный finish; повторное использование индекса с новым ID; direction mismatch без phantom row; поздний release после reuse при занятом slot; `RELEASED(A) → DSCI ACTIVE(B)` первым событием → busy snapshot → повторный `ACTIVE(B)` с двумя durable IDs и одной MT row; no-channel release при подтверждённом пустом slot; пропуск старого CLCC snapshot; malformed snapshot с одновременно видимым занятым slot, затем корректная пустая повторная проверка; сброс/retry состояния при ошибке старого и актуального CLCC (включая ERROR/TIMEOUT path); recovery после рестарта; отложенная foreign-key ошибка на COMMIT с проверкой rollback статуса. Отдельный `ctq_clcc_parser_test` вызывает production strict parser, проверяет полностью валидную строку, trailing garbage `145junk`, кавычки, лишние поля, overflow и invalid enum; затем связывает parse failure с invalid snapshot, retry и единственным finish после валидного empty snapshot. `call_log_direction_matches()`, `call_log_incoming_is_new_generation()`, `call_log_start_new_generation()`, `call_log_release_snapshot_decide()`, `call_log_release_should_finish()` и SQL finish вызываются production path и тестом — это seams классификации/correlation/persistence, не подмена Asterisk callback.

Unit tests вызывают production strict parser и единый production generation-decision helper, а также SQLite persistence seams, но не запускают скрытые static callbacks `at_response_clcc()`/`at_response_dsci()`/CCINFO, Asterisk taskprocessor и serial reader. Не эквивалентны сквозной проверке: разбор реальных +CLCC/^DSCI/+QIND строк, interleaving unsolicited release с частичным CLCC response, запуск/отказ `ast_pbx_start()`, фактический app timeout и физический caller abandon. Для этих проверок нужны Asterisk runtime и модемный serial stream; test harness не обладает реальным channel scheduler, AT queue response framing или поколением modem event. Ручные вызовы SQLite helper подтверждают только production-used persistence/classification seam. Устройство не использовалось.
