# Входящие SMS: сохранение частей, очередь и безопасная очистка SIM (шаг 2)

## Назначение и границы

Шаг обеспечивает надёжный путь с сохранением данных входящих SMS из физического SIM-хранилища `SM`: уведомление модема → чтение ячейки → транзакционное сохранение сегмента → сборка составного сообщения → надёжная запись полного текста в `mt_queue` → команда удаления → проверка фактического состояния ячейки → повтор или удаление завершённой группы. Удаление разрешается только настройкой `sms_autodelete`. Хранилище `ME` не обрабатывается. `RES_CMT` содержит прямое уведомление без адресуемой SIM-ячейки, поэтому удалить его через `CMGD` невозможно и не следует.

Реализация не обещает доставку ровно один раз. Маркер группы предотвращает повторное добавление сообщения при обычном повторном чтении сохранённой группы. После полной очистки группы позднее повторно появившаяся на модеме SMS уже не имеет соответствующего маркера; повторная постановка в очередь в таком случае остаётся допустимой неоднозначностью. Тесты не работают с реальным модемом.

## Схема `incoming_msg`

Старые строки мигрируются идемпотентно. Для исторических строк новые поля источника остаются `NULL`, поэтому такие строки не превращаются в задачи удаления. Составной первичный ключ остаётся `(key, seqorder)`; индекс `incoming_key` ускоряет поиск частей группы.

| Поле | Формат и смысл |
| --- | --- |
| `key` | Стабильная группа multipart: идентичность SIM/модема, отправитель, concat reference и число частей. Это не внешний URL. |
| `seqorder` | Номер сегмента в SMS. Сборка использует `ORDER BY seqorder`; дополнительная строгая проверка полного множества `1..N` не добавлена. |
| `expiration` | Время истечения временной строки в секундах от начала начала Unix epoch. |
| `message` | Текст одной части, не обязательно полное сообщение. |
| `source_device`, `source_storage`, `source_index` | Устройство и исходная ячейка. Для задач удаления хранилище должно быть `SM`; старые/неадресуемые строки имеют `NULL`. `source_index` — индекс модема, а не постоянный идентификатор. |
| `delete_status` | Числовой статус из `sms_delete_state.h`; сохраняемые коды нельзя менять без миграции. |
| `delete_attempts` | Подтверждённые ошибки: CMGD завершился ошибкой/тайм-аутом, свежее чтение нашло SMS, повторное сохранение завершилось фиксацией. Ошибка чтения/БД не учитывается. |
| `retry_at` | Время следующего действия планировщика, секунды от начала начала Unix epoch. |
| `mt_queued` | Для группы надёжно создана полная запись `mt_queue`; это условие очистки, не состояние доставки Flexisip. |
| `mt_mid` | MID записи очереди группы; повторное чтение использует его повторно. До фиксации очереди поле `NULL`/пустое. |

### Состояния удаления

| Код / enum | Смысл и следующий безопасный шаг |
| --- | --- |
| `0 PENDING` | Первый проход либо присутствие после восстановления без подсчёта; сохранить ячейку и поставить новую CMGD. |
| `1 VERIFY` | Предыдущая CMGD завершилась `ERROR`/`TIMEOUT`; выполнить новое чтение CMGL/CMGR. |
| `2 COMPLETE` | CMGD получил `OK` либо новое чтение подтвердило пустоту; группа может быть очищена при наличии маркера очереди. |
| `3 STOPPED` | Пять подтверждённых ошибок; автоматика остановлена, строка остаётся для диагностики. |
| `4 CMGD_SENT` | Команда могла выполниться; после перезапуска только свежее чтение, никогда повтор старой CMGD. |
| `5 VERIFYING` | Проверка после известной ошибки CMGD; присутствие с последующей фиксацией учитывается. |
| `6 VERIFYING_UNCOUNTED` | Неоднозначная команда, перезапуск или первичная проверка; присутствие не расходует лимит. |

Переходы задаёт `sms_delete_state_apply()`. `VERIFY_PRESENT_SAVED` увеличивает счётчик только в состоянии 5: только оно доказывает предыдущую ошибку CMGD. В состоянии 6 переход возвращает строку в pending без подсчёта. `VERIFY_ABSENT` завершает удаление. Отказ постановки в очередь, ошибка чтения и ошибка БД не считаются ошибками удаления.

## Поток, транзакции и восстановление

1. При `+CMTI` принимается только storage `SM`; имя сохраняется с индексом. Перед `CMGR`/`CMGL` явно выбирается `SM`; `ME` не входит в путь удаления.
2. `CMGR`/`CMGL` возвращают сегмент. Вспомогательная функция БД сохраняет текст, `key`, `seqorder` и идентичность источника. `sms_multipart_put()` возвращает неполное число строк, пока `count != parts`; при полном количестве склеивает в порядке `seqorder`. Для поступления `1,3,2` сборка появляется только после последней недостающей части и даёт `1+2+3`.
3. Вызов smsdb держит общий мьютекс SQLite от `BEGIN` до `COMMIT` или `ROLLBACK`, включая вставку/сборку. Успешный возврат означает, что данные надёжно сохранены. Ошибка записи/фиксации не разрешает CMGD и не отправляет отдельную часть как полную SMS.
4. После сборки под тем же мьютексом проверяется стабильный маркер. Если он есть, используется прежний `mt_mid`; иначе выбранный MID, запись MT и маркер создаются одной транзакцией. Удаление сегментов допустимо только после долговечной фиксации маркера. Доставка MT через Flexisip и её повторы не являются условием очистки.
5. После фиксации сохранения/очереди ставится `CMGD` для точных хранилища/индекса и сохранённого rowid. Отказ AT-очереди возвращает строку в повторяемое состояние.
6. Ответ `CMGD OK` завершает удаление. `ERROR`/`TIMEOUT` переводит задачу на новое чтение; старую команду не повторяют. Пустая ячейка означает успех. Если SMS присутствует, её снова сохраняют и лишь затем ставят новую CMGD. В лимит входят только подтверждённые присутствием ошибки после известного отказа CMGD.
7. После перезапуска выборщик выбирает строки, для которых наступило время повтора, включая `CMGD_SENT`; результат старой команды не угадывается по статусу, текущая ячейка читается заново. `CMGD_SENT` восстанавливается без подсчёта.
8. Если устройство отсутствует, не инициализировано/занято или выключен `autodelete`, меняется только `retry_at`. Счётчик/статус сохраняются, AT не отправляется, следующий проход доступен другой SIM.
9. Ошибки БД/COMMIT/чтения оставляют строку доступной для повтора и запрещают удаление. Временная ошибка до первого сохранения может храниться в состоянии повтора чтения этого устройства в процессе; уже сохранённые строки восстанавливаются из БД.

### Владение SQLite и блокировками

`src/sms_incoming_schema.c` сам не захватывает мьютекс и не завершает транзакцию. Вызывающие функции из `smsdb.c` обязаны сериализовать доступ к соединению и включать изменения в свою транзакцию. `db_create()` оборачивает миграцию в `SMS_TX_SCOPE`; `smsdb_put_internal`, `smsdb_incoming_delete_apply` и `smsdb_mt_queue_incoming_group` удерживают мьютекс соединения от начала транзакции до фиксации/отката. Владение операторами и буферами описано в заголовках: операторы закрываются до возврата, собранный буфер освобождается через `sqlite3_free()`, входные строки принадлежат вызывающей стороне.

`UPDATE incoming_msg` связывает значения параметрами `?`; обновление удаления требует rowid и совпадения устройства/хранилища/индекса (`IS` корректно сравнивает значения, допускающие NULL). Это не позволяет старому AT-ответу изменить другую строку после повторного использования индекса модемом. Ключ группы, устройство и время также передаются параметрами, а не вставляются в строку SQL. Сборщик мусора группы удаляет группу только при `MIN(mt_queued)=1` и полном числе строк со статусом complete; одна пустая ячейка не удаляет остальные сегменты.

## Тесты и проверяемые инварианты

- `sms_multipart_test`: миграция старой схемы, привязка UPDATE к rowid/идентичности источника, отсутствие сборки после `1,3` и итог `123` после части `2`, ошибки БД/фиксации без ложного успеха.
- `sms_delete_state_test`: CMGD OK/подтверждённая пустота без расхода попыток, пять подтверждённых ошибок, восстановление `CMGD_SENT` без подсчёта, ошибки постановки/чтения/БД без расхода лимита.
- `sms_delete_flow_test`: последовательность обратных вызовов (`S`,`Q`,`D`,`A`,`R`), отсутствие частичной доставки, `sms_autodelete`, только `SM`, исключение RES_CMT и проверка исходной идентичности, ошибки и восстановление.
- `sms_delete_flow_sqlite_test`: настоящая схема SQLite; части сохраняются до постановки MT-записи в очередь и подтверждения пустоты всех ячеек; запись MT и маркер создаются атомарно; проверяются сбой фиксации, справедливость планировщика, ошибки маркера, восстановление, параметры SQL, изоляция повторов и восстановление `CMGD_SENT`.

## Сборка

Из корневого каталога драйвера при наличии заголовков Asterisk:

```sh
cmake -S . -B /tmp/ctq-step2-build \
  -DCMAKE_INCLUDE_PATH=/path/to/asterisk/include \
  -DCMAKE_C_FLAGS=-I/path/to/asterisk/include
cmake --build /tmp/ctq-step2-build -j4
ctest --test-dir /tmp/ctq-step2-build --output-on-failure
```

Только цели SQLite собираются без Asterisk; библиотека боевого кода требует корневой каталог заголовков Asterisk. Тесты не выполняют развёртывание, не подключаются к реальному модему и не проверяют аппаратно-зависимые ответы AT. Управление сокет/AT остаётся интеграционной границей.
