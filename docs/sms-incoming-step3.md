# Просмотр накопленных сегментов входящих SMS (шаг 3)

## Назначение и границы

`incoming_msg` содержит сохранённые строки отдельных частей SMS, ещё не удалённые сборщиком мусора после успешной записи полной группы в очередь и подтверждения пустоты всех SIM-ячеек. Шаг 3 добавляет просмотр этих строк в уже существующий mini-web. Страница предназначена для диагностики multipart сборки и удаления: она не меняет состояния и не назначает повторы, не запускает AT-команды и не создаёт второй слушающий сокет или порт. Старые `/json` и `/sms` остаются отдельными маршрутами с прежним содержимым; новая страница не подменяет общую историю из `mt_queue` и `mt_out`.

## URL, фильтры и HTTP ответы

| Запрос | Результат |
| --- | --- |
| `GET /sms/parts` | HTML всех сохранённых частей всех устройств. |
| `GET /sms/parts?page=N` | Та же HTML-страница с номером страницы `N`. |
| `GET /sms/parts.json?page=N` | Постраничный JSON всех устройств. |
| `GET /sms/parts/<sim>` | HTML-страница частей одного настроенного устройства SIM. |
| `GET /sms/parts/<sim>.json?page=N` | JSON частей выбранного SIM/device. |

Для SIM используется существующая проверка настроенного устройства и разбор одного безопасного компонента пути. Неизвестная SIM, пустое имя, slash/path traversal и лишний компонент дают `404 Not Found`, `text/plain`, `not found`. Параметр запроса `page` разбирается общими вспомогательными функциями обработки параметров запроса и целых чисел: отсутствующий, некорректный или неположительный ввод становится 1; допустимая страница ограничивается диапазоном `[1,pages]`. Размер страницы фиксирован — `10`; пустая выборка имеет `pages=1`, `total=0`, возвращает HTTP 200 и пустой список/пояснение. Имя устройства передаётся SQLite как параметр, а не как фрагмент SQL.

Ошибка подсчёта/страницы/оператора БД возвращает HTTP 500. Для JSON тело имеет тип `application/json`, содержит `{"error":"sms database unavailable"}` и отправляется с точной длиной без NUL. Для HTML-запроса используется `text/plain` и `internal error: SMS database unavailable`. Ошибка выделения массива/объекта/элемента JSON или сериализации также приводит к HTTP 500, а не к закрытию сокета без ответа либо успешной выдаче частичного/пустого JSON. Чтение не меняет строки, `retry_at`, счётчик ошибок удаления, маркер или очередь.

## JSON-конверт и поля записи

Пример ответа для страницы всех устройств:

```json
{
  "device": null,
  "page": 1,
  "page_size": 10,
  "total": 1,
  "pages": 1,
  "items": [
    {
      "rowid": 42,
      "device": "sim-A",
      "storage": "SM",
      "source_index": 7,
      "key": "multipart-group-key",
      "seqorder": 2,
      "message": "часть сообщения",
      "expiration": 1760000000,
      "delete_status": 0,
      "delete_attempts": 0,
      "retry_at": 1760000000,
      "mt_queued": true,
      "mt_mid": "stable-message-id"
    }
  ]
}
```

- Поле конверта `device`: выбранная SIM-строка либо JSON null для всех устройств. `page`, `page_size`, `total`, `pages` — числовые сведения о разбиении на страницы, `items` — текущие строки.
- `rowid`: идентификатор строки SQLite. `device`, `storage`, `source_index`: источник сегмента. Старые/отсутствующие значения SQL отображаются как пустая строка/ноль согласно проекции; для обычной строки удаления `storage="SM"`.
- `key`: ключ multipart-группы; `seqorder`: номер части, заданный декодером;  `message`: текст только текущей части.
- `expiration`, `retry_at`: секунды начала Unix epoch из схемы; ноль означает отсутствующее время повтора по умолчанию. `delete_status` — сохранённый код из `sms_delete_state.h`: 0 pending, 1 verify, 2 complete, 3 stopped, 4 CMGD_SENT, 5 verifying counted, 6 verifying uncounted. `delete_attempts` — подтверждённые ошибки, не все попытки чтения. `mt_queued` означает, что полное сообщение и маркер сохранены в очереди доставки MT; `mt_mid` — MID маркера либо пустая строка.

Строки JSON создаются средствами JSON API Asterisk (`ast_json_string_create`/`ast_json_dump_string_format`), поэтому кавычки, slash/UTF-8 и управляющие символы экранирует средство кодирования JSON, а не ручная конкатенация. Поля элемента берутся из проекции постраничного чтения; при ошибке выделения функция обратного вызова останавливает обход, средство отображения отбрасывает частичный массив и отвечает 500.

## Сортировка и разбиение на страницы

Используются два подготовленных шаблона SQL — для всех устройств и для выбранного устройства. В варианте с устройством применяется единственный фильтр — `WHERE source_device=?`; оба шаблона задают порядок `expiration DESC, key COLLATE BINARY ASC, seqorder ASC, rowid ASC`, затем `LIMIT ? OFFSET ?`. Более поздние expiration идут первыми, сегменты одной группы располагаются последовательно, а одинаковые key/seqorder разрешаются по rowid. Устройство, limit и offset передаются отдельными параметрами. Подсчёт и выборка страницы используют одинаковые правила: `NULL`/пустое имя означает все устройства; незнакомое имя без совпадений даёт корректный пустой результат, а не ошибка SQL.

HTML-ссылки сохраняют фильтр устройства и формат страницы; ссылки JSON, Next и Previous создаются используемой в боевом коде вспомогательной функцией построения URL. `web_util_page_meta` вычисляет offset и ограничивает page по той же схеме, что существующие страницы истории `/sms`.

## Реализация и назначение файлов

| Файл | Назначение |
| --- | --- |
| `src/sms_incoming_paging.[ch]` | Независимые от Asterisk операции боевого кода для подсчёта/выборки SQLite; оператор живёт только внутри вызова, значения копируются в ограниченную структуру строки, обратный вызов видит копию до возврата. |
| `src/smsdb.[ch]` | Обёртка боевого кода держит общий мьютекс соединения во время подсчёта/выборки и передаёт ошибку веб-уровню; транзакция записи не начинается. |
| `src/web_incoming_parts.[ch]` | Чистые контракты, используемые боевым кодом: классификатор нового пути, точные тела/длины 404/500, экранирование HTML и построение ссылок страниц. Старые маршруты не классифицируются. |
| `src/mt_task.c` | Диспетчер существующего слушающего сокета Asterisk, HTML-таблица, JSON-конверт/элементы, обработка ошибок БД и навигационная ссылка. Перед чтением проверяются имя SIM и наличие устройства. |
| `src/CMakeLists.txt` | Добавляет новые вспомогательные C-файлы боевого кода в библиотеку драйвера. |
| `test/sms_incoming_paging_test.c` | Проверяет постраничный модуль боевого кода на настоящей схеме SQLite в памяти. |
| `test/web_incoming_parts_test.c` | Проверяет те же чистые вспомогательные функции, которые использует средство отображения/диспетчер боевого кода. |
| `test/CMakeLists.txt` | Регистрирует `sms-incoming-paging` и `web-incoming-parts` в CTest. |

Модуль постраничного чтения сам не захватывает мьютекс: обёртка `smsdb` боевого кода сериализует соединение, а модульный тест владеет отдельным соединением SQLite. Строки копируются во встроенные поля структуры, оператор закрывается после обхода, владение БД и контекст обратного вызова модулю не передаются. Существующие функции обратного вызова и SQL истории SMS не менялись.

## Безопасность HTML и граница модульного тестирования

Каждое значение БД в текстовой ячейке HTML проходит через функцию боевого кода `web_incoming_html_escape`: `&`, `<`, `>`, `"`, `'` заменяются безопасными HTML-последовательностями, байты UTF-8 сохраняются. Ссылки в HTML-атрибуты формируются вспомогательной функцией построения URL и затем экранируются; устройство допускается только после проверки настроенной SIM/разбора имени. Числа форматируются как числа. Текст сегмента не вставляется в тег/атрибут.

`web_incoming_route()` распознаёт только семейство `/sms/parts...`; `tail` указывает на исходный суффикс SIM-пути, а режим ответа определяется конечным `.json`. Вызывающая сторона отдельно проверяет имя и наличие настроенной SIM, поэтому некорректный tail получает 404. Тесты проверяют классификатор боевого кода, экранирование HTML, построение URL и точные статус/MIME/длину тела ответов 404/500, включая пропуск старых маршрутов без обработки для `/sms` и `/json`.

## Тесты и точная граница интеграции

`test/sms_incoming_paging_test.c` создаёт настоящую таблицу `incoming_msg` и проверяет сопоставление полей/значения по умолчанию для NULL, фильтрацию всех устройств и одной SIM, кавычки/управляющие символы во входных данных, изоляцию устройств, устойчивый порядок с разрешением равенства по rowid, первые/средние/последние страницы и страницы за пределами диапазона, граничные смещения, досрочное завершение обратного вызова, пустую таблицу/неизвестное устройство, отсутствующую/неполную схему, ошибки чтения, вызванные авторизатором, некорректные аргументы и отсутствие изменений БД.

`test/web_incoming_parts_test.c` проверяет используемые вспомогательные функции боевого кода: классификацию путей и обход старых маршрутов, режим HTML/JSON, имена SIM с точкой, `.jsonx`, пустой суффикс, ответы 404/500 с точной длиной, экранирование HTML от XSS с UTF-8/управляющими символами/усечением, создание URL и границы буфера.

Модульные тесты проверяют, что классификатор пропускает `/json` и `/sms` дальше, но **не проверяют поведение старых обработчиков через сокет** и не выполняют HTTP-запросы к этим маршрутам через сокет. Они также не создают TCP-клиент для `mt_web_serve_client` и не загружают средство отображения Asterisk `ast_json` для сравнения сериализованных байтов конверта. Проверяемые границы покрываются тестами используемых классификатора/экранирования/URL/обработки ошибок и SQL боевого кода на SQLite; JSON-строки строятся через JSON API Asterisk, а не собственным средством сериализации. Сквозная проверка слушающего сокета, HTTP-заголовков/жизненного цикла соединения и реальных ошибок выделения памяти в процессе Asterisk остаётся интеграционной границей.

## Сборка и локальная проверка

```sh
cmake -S . -B /tmp/ctq-build \
  -DCMAKE_INCLUDE_PATH=/path/to/asterisk/include \
  -DCMAKE_C_FLAGS=-I/path/to/asterisk/include
cmake --build /tmp/ctq-build -j4
ctest --test-dir /tmp/ctq-build --output-on-failure
git diff --check
```

Чистые тестовые вспомогательные модули можно собирать без тяжёлых зависимостей; библиотека боевого кода требует дерево заголовков Asterisk. Шаг не добавляет HTTP-слушающий сокет/порт, развёртывания или действий с модемом.
